# Pilot Hotel Rehearsal

Last updated: 2026-07-27

## Objective

Define a representative end-to-end Sevvn pilot rehearsal for one hotel, using the active runtime paths that already exist in code.

This document closes Task 11 from `tasks/plan-sevvn-30-day-pilot.md` by turning the pilot flow into:

- one canonical hotel scenario
- one operational setup order
- one guest journey validation path
- one pass/fail checklist for pilot readiness

## Canonical Pilot Hotel

Use one standard pilot tenant profile instead of trying to validate the whole catalog at once.

- Hotel profile: independent hospitality property with reception-operated room allocation
- Canonical live rehearsal tenant on 2026-07-27: `Konekto Hotel`
- Plan preset: `premium`
- Initial template: `aura`
- Allowed pilot modules: `hotel_info`, `messages`, `room_service`, `restaurant`, `services`, `bookings`, `profile`, `basic_notifications`
- Controlled modules allowed only with explicit narrative: `spa`, `tours`, `promotions`
- Excluded from rehearsal success criteria: `wallet`, `loyalty`, `concierge`, `events`, `digital_checkin`, `digital_checkout`

Live-prep companion:

- [konekto-hotel-live-rehearsal-prep-2026-07-27.md](/abs/path/C:/ProjetosFlutter/konekto_app/docs/konekto-hotel-live-rehearsal-prep-2026-07-27.md)

## Rehearsal Principle

The rehearsal is successful only if the hotel can be configured and then used through real backend-backed paths.

The rehearsal is not satisfied by:

- asset-mode guest validation
- template-only demo screens
- catalog presence without active runtime proof
- mock wallet or loyalty surfaces

## Required Setup Order

### 1. Platform admin onboarding

Create the hotel through `POST /api/platform-admin/hotels`.

Expected outcome:

- a new hotel record is created with a fresh `hotelId`
- the first manager (`gerente`) is created atomically
- the initial template is `aura`
- the initial subscription is created in `trial`
- a one-time temporary password is returned for the manager
- the mutation leaves an audit log

Evidence in code:

- `apps/konekto_api/app/api/platform-admin/hotels/route.ts`
- `apps/konekto_api/app/api/platform-admin/hotels/route.test.ts`

### 2. Subscription and preset confirmation

Confirm or update the subscription through `PATCH /api/platform-admin/hotels/[hotelId]/subscription`.

Required rehearsal state:

- the hotel ends up on a preset that exposes the intended template and module set
- `premium` is the recommended rehearsal baseline because it avoids artificial template/module lockouts during validation

Evidence in code:

- `apps/konekto_api/app/api/platform-admin/hotels/[hotelId]/subscription/route.ts`

### 3. Portal staff access

Use the manager credentials to access the hotel portal.

Required rehearsal checks:

- portal authentication succeeds with the newly created hotel manager
- hotel-scoped APIs respect the manager hotel boundary
- the portal can resolve the hotel config from `GET /api/hotels/[hotelId]`

Evidence in code:

- `apps/konekto_api/app/api/hotels/[hotelId]/route.ts`
- `apps/konekto_portal_next/hooks/useHotelConfig.ts`

### 4. Hotel visual and module setup

Inside the portal, configure:

- branding basics
- one allowed template
- pilot-safe module toggles

Required rehearsal checks:

- selected template is allowed by the active preset
- guest-facing config resolves `enabledModules`
- disallowed modules stay blocked by backend rules, not only by UI

Evidence in code:

- `apps/konekto_portal_next/app/(portal)/settings/appearance/page.tsx`
- `apps/konekto_portal_next/app/(portal)/settings/modules/page.tsx`
- `apps/konekto_api/app/api/hotels/[hotelId]/route.ts`

### 5. Room registry

Register at least one physical room in the hotel portal.

Required rehearsal checks:

- room creation succeeds through the real room registry path
- the room becomes available for occupancy/stay creation

Evidence in code:

- `apps/konekto_portal_next/app/(portal)/settings/rooms/page.tsx`

### 6. Stay opening and first guest creation

Use the room occupancy flow to:

- open a stay for a free room
- create the first guest in that stay
- generate the guest access code

Required rehearsal checks:

- stay creation happens before guest creation
- the guest is linked to the created stay
- an access code is generated by the backend
- the room becomes occupied in operational views

Evidence in code:

- `apps/konekto_portal_next/components/rooms/OccupancyForm.tsx`
- `apps/konekto_api/app/api/hotels/[hotelId]/stays/route.ts`
- `apps/konekto_api/app/api/hotels/[hotelId]/guests/route.ts`
- `apps/konekto_portal_next/components/rooms/OccupancyForm.test.tsx`

### 7. Additional guest handling

Optionally add a second guest to the active stay from the guest list flow.

Required rehearsal checks:

- the portal only allows guest creation when at least one active stay exists
- multiple guests can belong to the same stay

Evidence in code:

- `apps/konekto_portal_next/app/(portal)/guests/page.tsx`
- `apps/konekto_portal_next/app/(portal)/guests/page.test.tsx`

### 8. Guest claim in the app

Use the generated access code in the guest app against the real backend claim route.

Required rehearsal checks:

- claim succeeds only for an active, non-revoked guest
- an expired or revoked stay is rejected
- a guest token is returned
- room number and Wi-Fi payload are returned from real backend data

Evidence in code:

- `apps/konekto_api/app/api/guest/claim/route.ts`
- `apps/konekto_api/app/api/guest/claim/route.test.ts`
- `apps/konekto_mobile/README.md`

Important runtime rule:

- the guest app must run with `APP_RUNTIME_MODE=api`

### 9. Guest-use pilot flows

After a successful claim, validate only the pilot-safe flows.

Minimum required guest-use scope:

- load hotel branding/config from the backend
- see stay and Wi-Fi information
- access enabled navigation/modules
- use room service
- use restaurant booking/availability flows
- use notices/messages/basic counters

Allowed but not required for rehearsal success:

- `spa`
- `tours`
- `promotions`

Not part of success criteria:

- `wallet`
- `loyalty`
- `concierge`
- `events`

## Pass Criteria

Task 11 should be treated as complete when the team can truthfully say all of the following:

- one hotel can be created without reusing template seed data
- that hotel can receive a real subscription/preset state
- a manager can enter the portal and configure template/modules
- the hotel can register rooms
- the hotel can open a stay and create at least one guest
- the guest receives a real access code
- the guest can successfully claim access in API mode
- the guest experience after claim is limited to pilot-safe modules and matches the public narrative

## Fail Conditions

The rehearsal should be considered failed or blocked if any of the following happens:

- validation depends on asset mode
- a newly created hotel cannot reach a usable portal state
- room occupancy cannot create a stay plus first guest in sequence
- guest claim succeeds for revoked/expired state
- pilot marketing or operational docs imply unsupported modules are live
- template selection appears successful in UI but is rejected by backend plan rules

## Recommended Canonical Scenario

Use the following canonical desk-validation scenario for all future pilot checks:

1. Create one premium pilot hotel in Sevvn Admin.
2. Keep template `aura` for the first pass.
3. Enable only pilot-safe modules plus any explicitly controlled module being demonstrated.
4. Register room `101`.
5. Open a stay for room `101`.
6. Create guest `Ana Silva` and capture the generated access code.
7. Claim in the guest app with `APP_RUNTIME_MODE=api`.
8. Validate home load, hotel info/Wi-Fi, room service, restaurant, messages, and notices.
